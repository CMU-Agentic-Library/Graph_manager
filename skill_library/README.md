# Skill Library v1

## Authoritative contracts and generated catalog

[`skills/`](skills/) holds nine authoritative JSON Contracts for task-level ZenoBench capabilities. Each Contract records `id`, `name`, `description`, `inputs`, `requires`, `checkable_requires`, `achieves`, `outcomes`, `executor`, and `verifier`. The source-function location is recorded for provenance. A Contract describes a capability the model may choose as a task-graph node; internal helpers and local callbacks in `skills.py` have no Skill Contract.

[`types.json`](types.json) defines the input types used by those nine Contracts. [`skill_library.json`](skill_library.json) is the complete model-facing catalog generated by [`build.py`](build.py). It contains descriptions, input types, and conditional connection hints, while omitting executor, verifier, and source paths. The runner will use the authoritative Contract for execution binding.

From the repository root, rebuild and check the catalog with:

```bash
python3 skill_library/build.py
python3 -m unittest discover -s tests
```

The generator validates Contract IDs, required fields, input type references, machine-checkable requirement bindings, and connection targets. Edit an individual Contract and rebuild the aggregate; do not edit the aggregate directly.

`checkable_requires` contains only conditions the validator implements. For example, `{"kind":"nonzero_vector","input":"displacement_xy"}` checks a proposed argument directly. `{"kind":"fact","predicate":"holding","args":{"object":"object"}}` binds the Contract's `object` input to an observed `holding` fact. A missing fact means the condition is unknown; it is never interpreted as false.

## Graph meaning

A Library connection is a conditional hint between Skill types. The current catalog has 10 connection groups, representing 17 directed links among the nine Skills. The viewer draws all nine nodes and these documented links as an overview. The links are useful composition examples, not a complete list of possible transitions or guarantees for every scene.

The overview is separate from a runtime task DAG. The model receives an observation, goal, and Library, then proposes all semantic Subgoals and their Skill Subgraphs in one `task_plan` JSON response. The proposed graph is checked against Skill IDs, input types, scene objects, and dependency cycles before execution. `depends_on` expresses the selected plan's ordering. Only conditions in `checkable_requires` with available evidence can produce a programmatic `precondition_failed` error; other `requires` remain descriptive until observation or runtime verification.

The repository documents Contracts, provides a catalog viewer, and statically validates model proposals. It does not yet include a graph runner or independent visual verifiers. Existing ZenoBench skill checks use privileged simulator state and annotations. Starting microwave heating alone does not establish a target food temperature. The microwave inspection capability currently uses a fixed pose.

The [planning loop](../README.md#planning-loop) consumes this generated public catalog, proposes one task DAG per semantic Subgoal, and statically checks the proposals. The authoritative Contracts remain the source for future execution bindings.

## Browse the catalog

```bash
python3 skill_library/viewer/server.py
```

Open `http://127.0.0.1:8765`. The local page searches the nine task-level Skills and shows their documented relationships. It reads the JSON catalog on every refresh and rebuilds it when a source Contract changes. The page polls every five seconds and has a manual Refresh button. The viewer uses only the Python standard library and does not send the Library to an external service.

For all 44 callable definitions and expressions in `skills.py`, including the 35 implementation details that are not Skills, see the [ZenoBench function inventory](../docs/zenobench-skills-function-inventory.md).
